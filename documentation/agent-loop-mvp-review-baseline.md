# Harness Agent-Loop MVP 建设与评审基线

## 1. 文档目的

本文档定义 Harness Agent-Loop MVP 的目标范围、必备基础设施、验收条件和评审输出格式，作为以下工作的统一依据：

- MVP 架构设计与技术选型；
- 实现完成度检查；
- Agent-Loop 框架评审；
- 版本回归与发布准入；
- 后续能力扩展时的兼容性判断。

本文描述的是**目标状态**，不代表仓库当前已经实现这些能力。评审结论必须引用代码、配置、测试结果或运行记录作为证据。

## 2. MVP 定位与范围

MVP 聚焦于：

> 单 Agent、持久化 Loop、受控工具调用、全链路可观测、可自动回归。

MVP 必须能够保证任意一次 Agent 运行均可被限制、暂停、恢复、审计、回放和自动评测。

### 2.1 MVP 范围内

- 单 Agent 多步骤执行；
- 模型决策与结构化 Tool Calling；
- Run、Step、Event 持久化；
- 工具注册、参数校验和受控执行；
- Run 内上下文管理；
- 权限策略与高风险操作审批；
- Artifact 管理；
- 执行时间线、成本和异常观测；
- Golden Cases 与自动回归。

### 2.2 MVP 非目标

- 多 Agent 协作和动态创建 Agent；
- 复杂 DAG 或低代码编排器；
- 跨任务长期记忆和向量数据库；
- Agent 自动修改 Prompt、Policy 或自身代码；
- 插件市场；
- 大规模分布式调度；
- 无人工约束的高风险自治操作。

非目标能力如果被提前实现，不得替代本基线中的必备能力，也不得降低安全、可恢复性和可审计性要求。

## 3. 规范用语

- **必须**：缺失即不满足 MVP 准入条件；
- **应该**：原则上需要满足，若不满足必须记录原因、风险和补齐计划；
- **可以**：可选能力，不影响 MVP 是否通过；
- **证据**：可复核的代码位置、配置、测试、日志、截图或 Run 标识；
- **通过**：要求已实现且存在有效证据；
- **不通过**：要求缺失、行为错误或没有可复核证据；
- **不适用**：仅在要求确实不适用于当前范围时使用，并必须说明理由。

## 4. 必备基础设施模块

### 4.1 Agent Runtime / Loop Engine

职责：驱动 `模型决策 → 工具执行 → 结果观察 → 下一步决策` 的完整循环。

必须满足：

- [ ] 支持多 Step Agent Loop；
- [ ] 支持结构化模型输出和 Tool Calling；
- [ ] 配置最大 Step 数、最长执行时间、Token 或费用预算；
- [ ] 每次循环均检查预算和终止条件；
- [ ] 支持成功、失败、取消、超时等明确终态；
- [ ] 工具错误能够标准化返回给 Runtime 和模型；
- [ ] 支持暂停、继续和取消；
- [ ] 不允许无限循环或无上限重试；
- [ ] 状态转换经过统一入口校验，非法转换被拒绝并记录。

建议最小状态集：

```text
CREATED
→ RUNNING
→ WAITING_TOOL / WAITING_APPROVAL
→ SUCCEEDED / FAILED / CANCELLED / TIMEOUT
```

### 4.2 Run State、Event 与 Checkpoint

职责：保证执行状态可持久化、可恢复、可审计。

必须满足：

- [ ] Run、Step、Event 持久化存储；
- [ ] 保存当前状态、当前 Step、输入、模型响应、工具调用和终止原因；
- [ ] Event 采用追加式记录，历史事实不可被静默覆盖；
- [ ] 支持 Checkpoint，或提供等效的确定性恢复机制；
- [ ] 服务重启后，未完成 Run 能恢复、重新入队或进入明确失败状态；
- [ ] 重复消息、重试或恢复不会造成相同副作用被重复执行；
- [ ] 状态修改具备并发保护，例如版本号、乐观锁或租约机制。

最小领域对象：

```text
Agent
Run
Step
Event
ToolCall
Artifact
Approval
```

### 4.3 Model Gateway

职责：屏蔽模型供应商差异，为 Runtime 提供统一模型接口。

必须满足：

- [ ] Runtime 不直接依赖具体供应商 SDK；
- [ ] 支持消息输入、Tool Calling 和结构化输出；
- [ ] 对结构化输出执行 Schema 校验；
- [ ] 支持超时、有限重试和明确失败；
- [ ] 记录模型名称、版本、参数、延迟、Token 和费用；
- [ ] 保存可审计的请求、响应或其安全脱敏版本；
- [ ] Agent/Run 能固定实际使用的模型和 Prompt 版本；
- [ ] 重试策略不会绕过 Run 的总预算。

MVP 可以只接入一个模型供应商，但统一接口是必需条件。

### 4.4 Tool Registry 与 Tool Executor

职责：定义 Agent 能调用的工具集合，并在受控边界内执行。

必须满足：

- [ ] 每个工具声明名称、描述、版本、输入和输出 Schema；
- [ ] 每个工具声明只读性、外部副作用和风险等级；
- [ ] 调用前校验工具是否注册、是否授权、参数是否合法；
- [ ] 调用受超时、输出大小和资源范围限制；
- [ ] 工具执行结果转换为统一 Observation 结构；
- [ ] 调用参数、结果、耗时、错误和工具版本可审计；
- [ ] 有副作用的工具具备幂等键、去重或等效保护；
- [ ] 工具不可通过模型输出绕过 Policy；
- [ ] 工作区文件访问和网络访问具有明确边界。

MVP 验证工具集至少包含：只读工具、工作区写入工具，以及一个模拟或真实的外部副作用工具。

### 4.5 Context Builder

职责：按照确定规则组装每一步模型调用的上下文。

必须满足：

- [ ] 统一组装 System Prompt、用户输入、历史 Step 和工具结果；
- [ ] 根据模型上下文窗口设置输入预算；
- [ ] 对过长消息和工具输出进行裁剪、摘要或拒绝；
- [ ] 保留关键约束、未完成目标和最新工具 Observation；
- [ ] 上下文中只包含当前 Run 有权访问的数据；
- [ ] 能追踪一次模型调用使用了哪些上下文来源；
- [ ] 摘要或裁剪不会静默改变事实，相关操作应可观测。

MVP 仅要求 Run 内工作记忆，不要求跨 Run 长期记忆。

### 4.6 Policy、权限与 Approval

职责：将模型提出动作与系统实际允许的动作分离。

必须满足：

- [ ] Policy 在工具真正执行前判定；
- [ ] 配置 Agent 可调用的工具白名单；
- [ ] 配置工具调用次数、时间、费用或资源限制；
- [ ] 文件、网络和外部系统访问范围可限制；
- [ ] 高风险操作进入 `WAITING_APPROVAL`，未经批准不得执行；
- [ ] 拒绝、批准、审批人、审批参数和时间均被记录；
- [ ] 继续执行前重新确认 Run 状态和授权有效性；
- [ ] 支持取消 Run 或停用 Agent 的基本 Kill Switch；
- [ ] Policy 拒绝不能由 Prompt、模型输出或工具实现覆盖。

### 4.7 Artifact Store 与版本化配置

职责：保存 Agent 产物和复现一次运行所需的配置引用。

必须满足：

- [ ] Artifact 内容与 Run 状态分离存储，Run 保存引用和元数据；
- [ ] Artifact 可关联到产生它的 Run、Step 和工具；
- [ ] Artifact 写入范围受 Policy 控制；
- [ ] Agent 配置包含模型、Prompt、工具和预算；
- [ ] Agent 配置具备稳定标识和版本；
- [ ] Run 固定并记录实际使用的 Agent、Prompt、模型、工具和 Policy 版本；
- [ ] Artifact 的覆盖、更新或删除行为可追踪。

### 4.8 Observability 与 Run Replay

职责：让开发者和评审者能够解释一次运行发生了什么。

必须满足：

- [ ] 可查看 Run 列表及单个 Run 的完整时间线；
- [ ] 可查看每个 Step 的状态、输入来源、模型结果和工具结果；
- [ ] 可查看状态转换、重试、审批、异常和终止原因；
- [ ] 展示 Token、费用和各阶段耗时；
- [ ] 日志中敏感字段经过屏蔽或受权限保护；
- [ ] 可通过 Run ID 关联日志、Event、Tool Call 和 Artifact；
- [ ] 支持基于持久化事实的回放或等效诊断，不要求重新触发副作用；
- [ ] 关键失败、预算耗尽和超时至少具有结构化日志。

MVP 可以使用管理 API、CLI 或简单调试页面，不要求建设完整运营前端。

### 4.9 Evaluation Harness

职责：用可重复测试验证 Agent、模型、工具和策略变更。

必须满足：

- [ ] 支持声明测试输入、初始环境和断言；
- [ ] 支持批量执行 Golden Cases；
- [ ] 优先支持确定性断言，如状态、文件、Schema、工具调用和预算；
- [ ] 同时覆盖成功路径、失败路径和拒绝路径；
- [ ] 保存每次评测使用的 Agent、模型、Prompt、工具和 Policy 版本；
- [ ] 保存测试结果和失败证据；
- [ ] 能比较至少两个框架或配置版本的结果；
- [ ] 关键回归集能够在 CI 或发布前自动执行；
- [ ] 不允许仅凭 LLM Judge 判定所有关键准入条件。

初始 Golden Cases 应覆盖至少以下场景：

1. 无工具的正常完成；
2. 多步工具调用正常完成；
3. 工具参数 Schema 不合法；
4. 工具超时或失败；
5. 高风险操作等待、拒绝和批准；
6. 最大步数、最长时间或预算耗尽；
7. 用户取消；
8. 服务重启后的恢复；
9. 重试不重复产生外部副作用；
10. 未授权文件、网络或工具访问被拒绝。

## 5. 端到端必验场景

评审时必须执行或提供以下场景的近期有效证据：

| ID | 场景 | 预期结果 |
|---|---|---|
| E2E-01 | 提交一个需要多个工具、持续多个 Step 的任务 | Run 正常完成，过程和产物可追踪 |
| E2E-02 | 执行过程中重启 Runtime | Run 恢复、重新入队或明确失败，不丢失状态 |
| E2E-03 | 模型请求高风险工具 | Run 暂停等待审批，批准前无副作用 |
| E2E-04 | 工具返回错误或超时 | 有限重试、降级或明确失败，不无限循环 |
| E2E-05 | 达到 Step、时间或费用上限 | Run 被安全终止，原因清晰可查 |
| E2E-06 | 重复投递同一工具调用 | 不重复产生不可逆副作用 |
| E2E-07 | 请求越权访问文件、网络或工具 | Policy 拒绝并记录完整证据 |
| E2E-08 | 查看已结束 Run | 能回放模型、工具、事件、审批和 Artifact 链路 |
| E2E-09 | 执行 Golden Cases | 自动输出通过率、失败原因、成本和版本信息 |

## 6. 评审硬门槛

出现以下任意一项，整体结论必须为“不通过”，不得由其他模块得分抵消：

1. Run、Step 或关键 Event 仅存在于进程内存；
2. 无法限制最大 Step、执行时间或资源预算；
3. 模型可绕过 Policy 直接执行工具；
4. 高风险副作用无需审批或等效硬性授权；
5. 工具重试可能重复产生不可逆副作用且无保护；
6. 服务重启后任务静默丢失，且没有明确恢复或失败机制；
7. 无法根据 Run ID 重建主要执行时间线；
8. Prompt、模型、工具或 Agent 配置不可确定版本；
9. 没有自动化 Golden Cases，或关键安全边界完全未测试；
10. 日志、上下文或 Artifact 存在已知未受控的密钥泄漏路径。

## 7. 评审方法与结论

### 7.1 逐项判定

每项要求必须记录：

| 字段 | 内容 |
|---|---|
| 条件 ID | 例如 `4.3-05` |
| 结论 | 通过 / 不通过 / 不适用 |
| 证据 | 文件、代码行、测试名称、Run ID 或日志引用 |
| 风险 | 缺失后可能造成的影响 |
| 整改建议 | 最小修复方案 |
| 负责人/计划 | 如已进入整改计划则填写 |

### 7.2 模块评级

- **A：完整**——模块必选项全部通过，并有自动化测试证据；
- **B：可用**——模块必选项全部通过，部分仅有人工或运行证据；
- **C：不完整**——存在必选项缺失，但未触发硬门槛；
- **D：不可接受**——触发硬门槛或模块核心能力不可用。

### 7.3 整体结论

- **通过**：所有硬门槛均未触发，九个必备模块均达到 A 或 B，所有端到端必验场景通过；
- **有条件通过**：硬门槛未触发，最多两个模块为 C，且缺口具有明确负责人、期限和临时控制措施；不得用于无人工监督的生产高风险操作；
- **不通过**：任一硬门槛被触发、任一模块为 D，或关键端到端场景失败。

“有条件通过”不能用于宣称 MVP 已完全完成，仅表示允许继续受控试运行或下一阶段开发。

## 9. MVP 完成定义

Harness Agent-Loop MVP 只有在以下条件同时成立时才视为完成：

1. 九个必备模块均达到 A 或 B；
2. 不触发任何硬门槛；
3. 九个端到端必验场景全部通过；
4. Golden Cases 可重复运行并输出版本化结果；
5. 任意 Run 均可被限制、暂停、恢复、审计、回放和自动评测。
